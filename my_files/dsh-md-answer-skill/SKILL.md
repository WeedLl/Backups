# md-answer — ответ как заметка

Скилл превращает ответ в файл, который не стыдно положить в хранилище Obsidian: одинаковый frontmatter, одинаковая структура, только те колауты, которые не сливаются друг с другом ни в Obsidian, ни в `treemd`, ни в `render-markdown.nvim` / `md-render.nvim`.

## 1. Когда срабатывать

Срабатывай, если выполнено хотя бы одно:

- **явная просьба**: «оформи», «сохрани в `.md`», «запиши в файл», «сделай заметку», «выгрузи», «в отдельный файл», `/md-answer`;
- **ответ большой**: примерно ≥ 60 строк, ≥ 4 смысловых разделов, или внутри таблицы / конфиги / пошаговый разбор, который будут перечитывать;
- **продолжение материала**: пользователь собирает курс, инструкцию или разбор и просит «продолжай» — новый кусок логично дописать в уже существующий файл.

Не срабатывай:

- короткий ответ на вопрос (1–10 строк), даже если он красивый;
- код, который просили «просто показать»;
- правка внутри уже существующего файла, если сохранение не просили, — правь сам файл, новый не создавай.

**Если непонятно, файл или чат** — задай **один** короткий вопрос с двумя вариантами («в `answers/` или просто в чат?») и по умолчанию считай, что файл нужен. Больше одного уточнения не задавай, работу не блокируй.

### Чей формат главнее

Правило одно: **формат пользователя главнее скилла**. Скилл — дефолт для случая, когда ничего не сказано.

| Что сделал пользователь | Что делать |
|---|---|
| Приложил файл формата или описал его словами | Взять за основу. Скилл — только для того, о чём там молчат |
| …и этот формат **похож на скилл** (колауты, frontmatter, `.md`-заметка) | **Спросить один раз**: «использовать скилл или совместить оба формата?» — и держаться ответа |
| …и формат **не похож** на скилл (CSV, список в чате, без markdown) | Просто выполнить. Скилл не включать |
| Сказал «оформи», «как обычно», «по скиллу», без деталей | Работает скилл |

**Совмещение** (когда пользователь выбрал «оба»): правило пользователя побеждает в конфликте, скилл добивает пробелы — имя файла, теги, TL;DR, оглавление, проверка. Если из-за пользовательского формата валидатор ругается:

- разрешены свои типы колаутов → `--allow=success,important` (перечислить через запятую);
- свои теги → `--no-vocab`;
- правило пользователя всё равно выше проверки: не ломай формат, отключи проверку и скажи одной строкой, что именно отключил.

**Явная просьба в сообщении** («без TL;DR», «не в `answers/`, а сюда») стоит выше и файла, и скилла.

## 2. Куда и как называть

- **Каталог**: `answers/` в текущем рабочем каталоге. Нет — создай (`mkdir -p answers`). Переопределение: переменная окружения `MD_ANSWER_DIR`.
- **Имя**: `YYYY-MM-DD-<слаг>.md`. Слаг — латиница, kebab-case, 3–6 слов по сути, без `answer`, `note`, `document`, `output`. Пример: `2026-11-08-vpn-na-vps.md`.
- **Дата**: бери из системы (`date +%F`), а не из головы; она же идёт в `created`.
- **Существующий файл не перезаписывай**: добавь `-2`, `-3`. Исключение — пользователь явно сказал «допиши в тот же файл».
- **В чат после записи**: путь в бэктиках + 1–2 строки, что внутри. Не дублируй весь текст ответа.

### Проверка дублей — до создания файла

```bash
ls answers/ 2>/dev/null
grep -H -m1 '^# ' answers/*.md 2>/dev/null | head -40
```

Если в `answers/` уже есть заметка на ту же тему (по заголовку или тегам) — **новую не заводи**. Допиши раздел в существующую (§7) или задай один вопрос: «дописать в `2026-11-01-vpn.md` или завести новую?». Пять заметок «про VPN» с разными датами — это не архив, а свалка.

## 3. Скелет файла

````md
---
tags:
  - ai/by_ai
  - sys/shell
created: 2026-11-08
---
# Заголовок: о чём заметка

> [!abstract] TL;DR
> 3–5 строк: что это, зачем, главный вывод.

## Содержание
- [[#Первый раздел]]
- [[#Второй раздел]]

## Первый раздел
...

## Источники
1. [Название](https://example.com) — что именно подтверждает.
````

Оглавление и «Источники» — не всегда, условия ниже.

## 4. Frontmatter

- `tags` — всегда содержит **`ai/by_ai`** первым: он помечает, что заметку написал агент, а не человек.
- Остальные 1–3 тега — **только реальные теги хранилища, переснятые в момент записи**. Каждый раз, без исключений и без «в прошлый раз было так»:

  ```bash
  node <каталог-скилла>/tools/tags.mjs --brief
  ```

  Вывод — одна строка: путь хранилища, число заметок и все теги. Кэша нет: читается только frontmatter, ≈0,15 с на 146 заметок.
- Валидатор сверяет теги **тем же живым пересъёмом**. Отдельно «освежать» ничего не нужно, но и брать список из памяти или из старого файла нельзя.
- Хранилище не нашлось: `tags.mjs` выходит с кодом 2 и печатает кандидатов, `check.mjs` даёт `vocab-unavailable`. В обоих случаях **спроси путь** (аргумент или `$OBSIDIAN_VAULT`), а не подставляй теги из головы.
- Тег выбирай **после** того, как текст готов, по сути разделов: `sys/shell/zsh` лучше, чем `zsh`, если в хранилище есть только первое.
- Выбранные теги перечисли в ответе одной строкой: «теги: `ai/by_ai`, `sys/shell` — предложение». Пользователь поправит, если мимо.
- Нужного тега в хранилище нет — не выдумывай молча: назови его как новый и спроси.
- Хранилище не нашлось (скрипт вышел с кодом 2 и напечатал кандидатов) — покажи кандидатов и спроси, какое брать; путь передавай аргументом или через `$OBSIDIAN_VAULT`.
- `created` — `YYYY-MM-DD`. При дописывании в старую заметку `created` не меняется: дата создания остаётся датой создания.
- Другие поля (`aliases`, `status`, `source`) — только если пользователь просил. Не добавляй `author`, `id` сам.

## 5. Текст

- **Один H1**, дальше `##`, при реальной необходимости `###`. H1 — тема («VPN на VPS за 15 минут»), не «Ответ» и не «Заметка».
- **TL;DR** — первый блок после H1, всегда `[!abstract]`, 3–5 строк, без воды. Это выжимка, а не повтор заголовка.
- **Оглавление** — `## Содержание`, только если разделов ≥ 5. Ссылки вида `[[#Заголовок]]`: Obsidian их понимает, остальные рендереры показывают текстом.
- **Таблицы** — для сравнений; **код** — в фенсах с языком; **шаги** — нумерованным списком.
- **Типографика**: «ёлочки» для цитат, длинное тире —, без эмодзи в заголовках, без CAPS-акцентов.
- **Источники** — `## Источники` в конце, если в тексте ≥ 2 внешних ссылок. Формат: `1. [Название](URL) — что подтверждает.` Локальные файлы — путём в бэктиках.

## 6. Callouts — только эти девять

| Тип | Когда |
|---|---|
| `note` | нейтральное дополнение по ходу текста |
| `abstract` | конспект: о чём раздел, если читать целиком лень (и TL;DR) |
| `todo` | что осталось сделать, пункт, который нельзя потерять |
| `tip` | приём, который экономит время |
| `question` | «почему так?» и разбор непонятного |
| `warning` | подводный камень: тут легко ошибиться |
| `danger` | необратимое действие, потеря данных |
| `example` | код, конфиг, сценарий использования |
| `quote` | слова другого человека |

**Других не бывает.** Самые частые рефлексы, которые надо погасить:

| Не пиши | Почему |
|---|---|
| `success`, `check`, `done`, `hint` | делят с `tip` один значок 💡 в treemd |
| `important` | в Obsidian отрисовывается как `tip` — дубль при живом `tip` |
| `caution`, `attention` | в treemd это 🛑 как у `danger`, в Obsidian — `warning` |
| `failure`, `fail`, `error`, `bug` | тот же 🛑, что у `danger` |
| `info` | в nvim тот же глиф и цвет, что у `note` |
| `tldr`, `summary` | алиасы `abstract` — пиши `abstract` |
| `faq`, `help` | алиасы `question` |
| `cite` | алиас `quote` |
| любой свой тип | в treemd получит нейтральный `❯`, в render-markdown вообще не станет колаутом |

Правила синтаксиса:

- тип строчными: `> [!warning]`, не `> [!WARNING]`;
- **без** `-`/`+` после `]` — treemd съедает маркер, render-markdown тащит дефис в заголовок;
- вложенность не глубже двух `>`;
- пустых колаутов не бывает: заголовок без тела — это не блок, а мусор;
- заголовок по-русски и не единственный различитель: в nvim свой заголовок заменяет подпись, и различимость держится на значке;
- между колаутом и соседним текстом — пустая строка.

Полная таблица «что с чем сливается» — `references/callouts.md`.

## 7. Дописать в существующую заметку

**Синонимы, на которых включается:** «допиши», «дополни», «добавь раздел/главу», «продолжай», «продолжение», «в тот же файл», «в эту заметку», «допиши сюда», «append», «продолжи заметку». А также когда проверка дублей нашла ту же тему.

1. Открой файл целиком, найди место: обычно конец, но если пользователь сказал «после раздела X» — туда.
2. Добавь **новый `##`-раздел**. Существующие блоки не переписывай: дописывание — это append, а не редактура.
3. Если новый материал меняет вывод — обнови `TL;DR` и объясни в чате, что именно поменял.
4. Добавь новый раздел в `## Содержание` (одна ссылка `[[#Раздел]]`), если оглавление есть.
5. `created` не трогай — дата создания остаётся прежней.
6. Не дублируй уже сказанное: если раздел с такой темой есть — дополни его, а не создавай второй.
7. Заметка выросла вдвое и тема расползлась (например, VPN и домашний сервер в одном файле) — предложи разделить, но сам не дели.

> [!warning] Чужие правки неприкосновенны
> Пользователь мог править файл руками. При дописывании меняй только то, что добавляешь, плюс TL;DR и оглавление. Молча «причесать» остальное — значит потерять его текст.

## 8. Перед сдачей

```bash
# каталог скилла = там, где лежит этот SKILL.md
node <каталог-скилла>/tools/check.mjs answers/2026-11-08-x.md
# если путь потерялся (типовая установка):
node "$HOME/.dsh/skills/md-answer_skill/tools/check.mjs" answers/2026-11-08-x.md
```

- **0 ошибок** → отдавай файл.
- **Ошибки** → почини и прогони снова. Не пиши «готово», пока валидатор красный.
- **Предупреждения** → почини, если это не меняет смысл; иначе оставь и упомяни одной строкой в ответе.

Флаги (полный список печатает `--help`):

| Флаг | Что делает |
|---|---|
| `--strict` | предупреждения считает ошибками |
| `--json` | машиночитаемый вывод, для скриптов |
| `--links` | проверяет живость внешних ссылок по сети, 4 параллельно, таймаут 8 с |
| `--no-vocab` | отключить сверку тегов с хранилищем (по умолчанию — живой пересъём) |
| `--allow=a,b` | разрешить дополнительные типы колаутов, если их задал пользователь |
| `--help` | список флагов и код выхода |

## 9. Частые провалы

- `[!success]` вместо `[!tip]` — самый частый рефлекс. Не надо.
- TL;DR из одного предложения-заголовка («В этой заметке про VPN») — это не выжимка.
- Оглавление в заметке на 40 строк — мусор.
- «Источники» без указания, что именно подтверждает ссылка.
- Дата в имени файла и в `created` разошлись.
- Файл перезаписан молча — потеря прежней версии.
- Тег придуман «по смыслу» вместо взятого из словаря хранилища.
- Вторая заметка на ту же тему вместо дописывания в первую.

## 10. Файлы скилла

- Папка скилла может называться иначе, чем `name` (например `md-answer_skill`): DSH берёт имя из frontmatter, каталог нужен только как база для `tools/` и `references/`.
- `references/callouts.md` — полная карта колаутов и почему набор именно такой.
- `examples/` — два эталона: короткая заметка и длинная с оглавлением и источниками.
- `tools/check.mjs` — валидатор, ноль зависимостей, Node ≥ 18.
- `tools/tags.mjs` — перепись тегов хранилища: читает только frontmatter, наружу отдаёт одну строку со списком.
- `tools/vault-tags.mjs` — общий модуль поиска хранилища и переписи; его же импортирует валидатор, поэтому кэша нет ни у кого.
