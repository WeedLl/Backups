# /dsh-update — обновление DSH без потери плагинов и скиллов

Скилл отвечает за один сценарий: обновить ядро, TUI и/или плагины так, чтобы после
этого **все профили (web, tui, headless) поднимались, все плагины грузились, а все
скиллы оставались на месте** — включая локальные форки, которые обновление может
затереть.

## 0. Когда срабатывать

- **Только по явному вызову** `/dsh-update` (или `/dsh-update <режим>`).
- Если пользователь говорит «обнови dsh», «проверь обновления», «апдейт» словами —
  **не запускай сам**: спроси «запустить `/dsh-update`?» и жди ответа.
- Никогда не запускай обновление по собственной инициативе, «попутно» или
  потому что увидел новую версию.

## 1. Железные правила

1. **Нет проверенного снимка — нет обновления.** `apply.sh` сам создаёт снимок и
   отказывается работать, если снимок не прошёл проверку. Не обходи это флагом и
   не «сэкономь время».
2. **Сначала `selftest.sh`.** Если он падает — скрипты устарели относительно
   текущего DSH. Остановись и скажи об этом, не импровизируй.
3. **Никогда не перезапускай TUI/web-сессию.** Обновление затрагивает файлы на
   диске; текущая сессия продолжает работать на старом коде. Перезапуск — только
   пользователь и только вручную.
4. **Локальные форки не обновляются автоматически.** `file:`-плагины
   (`dsh-session-alerts`, `dsh-session-delete`, `dsh-tui-pkg`) диагностируются и
   переустанавливаются только по явной просьбе.
5. **Мажоры и 0.x-minor — только с согласия.** Для пакетов < 1.0.0 минорный
   апгрейд считается ломающим.
6. **Правки — только в исходниках.** Не редактируй `node_modules`: следующее
   обновление это сотрёт. Если форк сломался — чини исходник и переинсталлируй.
7. **`latest` ≠ самая новая версия.** У ядра есть теги `latest` и `next`;
   обновление на `next` без проверки peer-диапазона TUI — способ получить
   нерабочую комбинацию.
8. **Один вопрос — одно решение.** Не задавай больше двух уточнений за раз и не
   блокируй работу вопросами, на которые можно ответить из отчёта.

## 2. Режимы

| Вызов | Что делает | Меняет файлы |
|---|---|---|
| `/dsh-update` или `/dsh-update check` | отчёт: что устарело, риски, рекомендация | нет |
| `/dsh-update verify` | проверка текущего состояния (конфиги, плагины, скиллы, smoke) | нет¹ |
| `/dsh-update update` | check → выбор → снимок → установка → проверка | да |
| `/dsh-update rollback` | откат из снимка | да |
| `/dsh-update selftest` | проверка допущений скилла | нет |
| `/dsh-update doc` | переписать журнал версий по текущему состоянию | да (только журнал) |

¹ `verify` перезаписывает `cordis.yml` профилей (штатное поведение любого запуска
профиля) и пишет отчёты в `~/.dsh/updates/reports/`.

Все команды ниже предполагают, что скилл установлен в `~/.dsh/skills/dsh-update`
(копия или симлинк на каталог скилла). Если путь другой — бери каталог, где лежит этот
`SKILL.md`.

## 3. Шаг 0 — selftest (всегда)

```bash
~/.dsh/skills/dsh-update/scripts/selftest.sh
```

Проверяет: есть ли `dsh`, поддерживаются ли `--profile`, `--dump-config`,
`dsh plugin --profile`, читаются ли профили, работают ли `collect.mjs` и `doc.mjs`,
есть ли `sha256sum`/`shasum` и `script`.

- **exit 0** — продолжай.
- **exit 1** — скрипты устарели. Покажи пользователю список расхождений и раздел
  «Если скрипты устарели» (ниже). Не обновляй DSH «вслепую» несовпадающими
  скриптами.

## 4. Шаг 1 — check

```bash
~/.dsh/skills/dsh-update/scripts/check.sh          # человекочитаемо
~/.dsh/skills/dsh-update/scripts/check.sh --json   # для разбора
```

Отчёт содержит:

1. **Сейчас** — версия ядра и способ установки, версия TUI и профиль, node/npm/pnpm.
2. **Доступные обновления** — `latest`/`next` ядра, `latest` TUI.
3. **Совместимость TUI ↔ ядро** — матрица `peerDependencies` (✓/✗/?). Это главный
   фильтр: если TUI не заявляет версию ядра, комбинация не поддерживается.
4. **Плагины с обновлениями** — по профилям, с типом (patch/minor/major) и риском.
5. **Локальные зависимости** — `file:`-пакеты, их исходники и версии.
6. **Предупреждения загрузчика** — то, что уже сломано *до* обновления.
7. **Скиллы** — невалидный фронтматтер, перекрытия имён.
8. **dsh_backup** — dry-run (`dsh_backup -n`) и покрытие: какие файлы состояния
   и каталоги ваш zsh-бэкап не копирует, с готовой строкой для патча.
9. **Рекомендация** — упорядоченный план с готовыми командами.

### Как читать отчёт

- **`next` новее `latest`** — это предрелиз. Обновлять на него только если TUI
  заявляет эту версию в peer-диапазоне; иначе скажи прямо: «ядро rc.N не
  поддерживается вашим TUI».
- **✗ в матрице** — не обновляй эту пару. Либо жди релиза TUI, либо обновляй оба
  компонента одновременно (порядок: TUI → ядро).
- **`0.x` + minor** — считай мажором.
- **`file:`** — обновление из npm затрёт форк (особенно `dsh-tui-pkg`, чьё имя
  совпадает с апстримом).
- **Предупреждения загрузчика** — это не «шум»: каждое означает плагин, который
  не подключился. Покажи их пользователю до обновления.

### Обязательный вопрос перед установкой

Всегда спрашивай (через `ask_user_question`), **кто выполняет установку**:

1. **«Сделаю сам»** — выполняешь `snapshot.sh` + `apply.sh` с подтверждением
   каждого шага (см. шаг 3).
2. **«Дай инструкцию»** — выдаёшь пошаговый блок команд с пояснениями, ничего не
   запуская. Пользователь выполняет сам, затем ты прогоняешь `verify.sh`.

И отдельно — **что именно обновлять**: только TUI, только ядро, выборочные
плагины, всё. Не выбирай за пользователя, если в отчёте есть ✗ или major.

## 5. Шаг 2 — снимок

```bash
~/.dsh/skills/dsh-update/scripts/snapshot.sh create --label pre-update
```

Снимок включает:

- конфиги всех профилей (`package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`,
  `cordis.yml`, `cordis.patch.yml`);
- домашний слой (`settings.yaml`, `cordis.patch.yml`, при `--with-secrets` —
  `.credentials.yaml`);
- **все скиллы** `~/.dsh/skills` (включая локальные, которых нет в `dsh_backup`);
- состояние TUI (`~/.dsh-tui`, кроме истории и логов);
- `manifest.json`: версии ядра/TUI/плагинов, baseline предупреждений загрузчика,
  список скиллов, покрытие `dsh_backup`;
- `checksums.txt`.

Сразу после создания снимок **самопроверяется**: контрольные суммы + пробное
восстановление в temp-каталог. Если проверка не прошла — обновление запрещено.

```bash
~/.dsh/skills/dsh-update/scripts/snapshot.sh list       # все снимки + общий размер
~/.dsh/skills/dsh-update/scripts/snapshot.sh show       # последний
~/.dsh/skills/dsh-update/scripts/snapshot.sh verify DIR # проверить вручную
~/.dsh/skills/dsh-update/scripts/snapshot.sh prune      # почистить старые
```

### Где это лежит и сколько хранится

- `~/.dsh/updates/snapshots/<дата>-<метка>/` — снимки (~300 КБ каждый);
- `~/.dsh/updates/reports/verify-<дата>/` — отчёты проверок (~50 КБ каждый);
- `~/.dsh/updates/snapshots/.latest` — указатель на последний снимок.

Политика хранения: **последние 5 снимков и 20 отчётов**. Старые удаляются
автоматически при создании нового снимка и в конце успешного обновления; снимок,
на который указывает `.latest`, не удаляется никогда — это точка отката.

Изменить лимиты:

```bash
DSH_UPDATE_KEEP_SNAPSHOTS=3 DSH_UPDATE_KEEP_REPORTS=10 .../snapshot.sh prune
# или разово посмотреть, что будет удалено:
.../snapshot.sh prune --keep 3 --keep-reports 10 --dry-run
```

## 6. Шаг 3 — установка

### Вариант А: как `/update`, но без перезапуска

```bash
~/.dsh/skills/dsh-update/scripts/apply.sh --official --yes
```

Запускает штатный апдейтер TUI (`dsh-tui update`): TUI → ядро → лаунчер, с его
собственными проверками (deadlock-диапазон, pre-seed `allowBuilds`, release-age,
верификация версии). Отличие от `/update` в TUI: **нет рестарта**.

### Вариант Б: точные версии и отдельные плагины

```bash
# TUI
~/.dsh/skills/dsh-update/scripts/apply.sh --tui 0.20.1 --yes

# ядро (способ установки определяется автоматически: npm или pnpm)
~/.dsh/skills/dsh-update/scripts/apply.sh --core 0.2.2-rc.1 --yes

# один плагин в конкретный профиль
~/.dsh/skills/dsh-update/scripts/apply.sh --plugin web:dsh-context@0.85.1 --yes
```

Без `--yes` — только план команд (dry-run). Порядок всегда: **TUI → ядро →
плагины**; при падении шага остальные пропускаются, чтобы не оставить смешанное
состояние.

### После установки

- `apply.sh` сам вызывает `verify.sh` (отключить: `--no-verify`) и переписывает
  журнал версий `doc/dsh-versions.md` (см. §13).
- В конце печатает путь снимка и команду отката.
- **Сообщи пользователю: нужен ручной перезапуск TUI/web.** Текущая сессия
  работает на старом коде, и её проверки не отражают новую версию до рестарта.

## 7. Шаг 4 — проверка

```bash
~/.dsh/skills/dsh-update/scripts/verify.sh --all
~/.dsh/skills/dsh-update/scripts/verify.sh --all --smoke
~/.dsh/skills/dsh-update/scripts/verify.sh --all --write-doc  # + журнал версий
```

Что проверяется:

| Проверка | Что ловит |
|---|---|
| `dump` | профиль не собирается: несовместимый плагин, битая зависимость |
| `bundles` | bundle объявлен, но пакета нет (или он есть только в host) |
| `deps` / `deps-lock` | пакет не установлен, версия расходится с lockfile |
| `peer` | версия ядра вне peer-диапазона TUI |
| `skill` | невалидный `SKILL.md`, перекрытие имён, скилл плагина перекрыт пользовательским |
| `loader-warning` | новые предупреждения загрузчика относительно базовой линии |
| `backup` | `dsh_backup` не покрывает новые файлы; `backup-run` — функция не запускается (`dsh_backup -n`) |
| `smoke` (с `--smoke`) | web не отвечает / плагин не активировался; TUI падает при старте; headless не отвечает |

`--smoke` делает живые прогоны:

- **web** — поднимает временный сервер на случайном порту, проверяет HTTP и
  строки `did not activate` / `failed to import` в stderr;
- **tui** — запускает TUI в псевдотерминале на 10 секунд;
- **headless** — один короткий прогон; без `DEEPSEEK_API_KEY` в окружении
  помечается `skip` (это не ошибка).

Живые прогоны запускают второй экземпляр приложения. Предупреди пользователя,
если у него уже открыт web/TUI: возможны конкурирующие записи в состояние.

Код выхода `1` — есть ошибки. Покажи их, не «сглаживай», и не перезапускай
сессию, пока они не разобраны.

`--write-doc` нужен после ручного `/update` внутри TUI: снимка до обновления
может не быть, тогда «до» берётся из предыдущей записи журнала. Ошибка записи
журнала не меняет код выхода проверки.

```markdown
Проверка: 0 ошибок, 4 предупреждения (dsh_backup не покрывает skills/ и storages/)

```

## 9. Откат

```bash
~/.dsh/skills/dsh-update/scripts/rollback.sh                # показать план
~/.dsh/skills/dsh-update/scripts/rollback.sh --yes          # восстановить файлы
~/.dsh/skills/dsh-update/scripts/rollback.sh --yes --reinstall  # + pnpm install по старым lockfile
~/.dsh/skills/dsh-update/scripts/rollback.sh --yes --core   # + откат глобального ядра
```

Перед восстановлением создаётся страховочный снимок `pre-rollback-*`. Файлы,
которых не было в снимке, не удаляются — только перезаписываются совпадающие.

**Если TUI сейчас запущен — попросите его закрыть перед откатом.** Работающий
интерфейс держит состояние в памяти и после отката перезапишет восстановленные
файлы `~/.dsh-tui` своим. Web-сервер безопаснее, но его тоже лучше остановить.

После отката `rollback.sh` сам переписывает журнал версий: строка `откат` в
истории и обновлённый раздел «Сейчас».

## 10. Локальные форки: что делать при поломке

`check.sh` показывает `file:`-зависимости и их исходники. Если после обновления
форк не грузится (в `verify --smoke` — `failed to import`):

```bash
# переустановить из локального исходника (по просьбе пользователя)
dsh plugin --profile tui add "file:/Users/weed/Documents/Ai/DSH/dsh-tui-pkg-ru"

# посмотреть, что именно сломалось
~/.dsh/skills/dsh-update/scripts/verify.sh --profile tui --smoke
```

Типовые причины: изменился экспорт в ядре (`does not provide an export named ...`),
переименован id в `cordis.patch.yml`, pnpm заменил форк версией из npm.

**Не «лечи» это правкой `node_modules`** — покажи diff исходника и предложи
обновить форк под новый API.

## 11. Если скрипты устарели

Признаки:

- `selftest.sh` вернул exit 1;
- `dsh --help` больше не содержит флагов, на которые опираются скрипты;
- `collect.mjs` падает или отдаёт пустые `bundles`;
- `dsh plugin` изменил синтаксис, `dsh --profile X --dump-config` — формат вывода.

Что делать:

1. Остановись. Не выполняй «похожие» команды по памяти.
2. Покажи пользователю, какой именно пункт `selftest` не сошёлся.
3. Предложи обновить файлы скилла в каталоге, откуда он установлен: посмотри
   `readlink ~/.dsh/skills/dsh-update` (симлинк) или сам каталог с `SKILL.md`.
   Правь исходник, затем переустанови `install.sh --link` или `--copy`.
4. Только после этого повторяй `/dsh-update`.

## 12. Ограничения и особые случаи

- **Права на запись.** Любой запуск профиля перезаписывает `cordis.yml`, поэтому
  `verify`/`apply` требуют доступа к `~/.dsh`. В песочнице возможен `EPERM` —
  тогда предложи выполнить шаг в своём терминале или выдать полный доступ.
- **Ключ модели.** Живой headless-прогон требует `DEEPSEEK_API_KEY` в окружении;
  без него smoke-тест помечается `skip`, а не `fail`.
- **Несколько профилей.** `--profile` можно повторять; без него проверяются все.
- **`headless`-профиль.** У него нет TUI; обновляется только ядро и его плагины.
- **`/update` внутри TUI.** Если пользователь уже обновился через `/update`,
  запускай `/dsh-update verify` — снимок до обновления в этом случае отсутствует,
  поэтому откат возможен только к последнему доступному снимку.
- **Время.** `check` ~5–15 с (сеть), `verify` ~2 с, `verify --smoke` ~40–60 с,
  `snapshot` ~2 с.
- **Снимок и сам скилл.** Снимок копирует скиллы, лежащие в `~/.dsh/skills`
  обычными каталогами. Если скилл подключён симлинком, его содержимое в снимок
  не попадает — держите рядом копию каталога.
- **Журнал версий.** Пишется best-effort: ошибка не отменяет обновление. В нём
  только версии, пути и результаты проверки — без токенов и ключей. Если `doc/`
  нет, скилл спрашивает Backup или answers (см. §13).

## 13. Журнал версий

После каждого обновления скилл переписывает заметку `dsh-versions.md`: ядро, TUI
и **все** плагины по профилям, «до → после» для текущего и предыдущего
обновления, результат проверки и снимок. Формат — Obsidian: `type: backup`,
`tags: [sys]`, `created` (дата), `time` (дата-время), TL;DR, таблицы и callouts.
Файл самодостаточен; `doc/` не обязан быть частью хранилища.

### Куда писать

| Приоритет | Условие | Путь |
|---|---|---|
| 1 | задан `DSH_UPDATE_DOC_DIR` | туда, каталог создать |
| 2 | `~/Documents/ForSys/Backup/doc/` существует | `Backup/doc/dsh-versions.md` |
| 3 | `doc/` нет, `Backup/` есть | **спросить**: `Backup/dsh-versions.md` (рекомендую) или `answers/dsh-versions.md` |
| 4 | `Backup/` нет | `answers/dsh-versions.md`, создать |

`answers/` — как у `md-answer`: `$MD_ANSWER_DIR` или `answers/` в рабочем
каталоге. Корень Backup можно переопределить `DSH_UPDATE_BACKUP_ROOT`, каталог
answers — `DSH_UPDATE_ANSWERS_DIR`. Выбор из пункта 3 запоминается в
`~/.dsh/updates/doc-target`, чтобы не спрашивать каждый раз. Если `Backup/doc` появится позже, приоритет 2 снова
выигрывает.

Рядом с заметкой лежит скрытый `.dsh-versions.json` — история для «предыдущего»
обновления и исходная дата `created`. Без него после второго обновления
«предыдущее» взять неоткуда.

### Команды

```bash
~/.dsh/skills/dsh-update/scripts/doc.sh path                  # куда писать
~/.dsh/skills/dsh-update/scripts/doc.sh write --snapshot DIR  # после обновления
~/.dsh/skills/dsh-update/scripts/doc.sh write --dir DIR       # выбрать fallback
~/.dsh/skills/dsh-update/scripts/doc.sh write --stdout        # посмотреть, не писать
```

`apply.sh` пишет журнал сам; ошибка записи не отменяет обновление. После ручного
`/update` внутри TUI — `verify.sh --all --write-doc`. После `rollback.sh` журнал
обновляется сам. Пропущенные мажоры передай в `apply.sh --skipped "pkg@ver
(причина)"` или в `doc.sh write --skipped ...` — они попадут в «Не обновилось».

Если `doc/` нет и выбор не сохранён, `apply.sh` предупредит: задай один вопрос
(Backup или answers), затем повтори `doc.sh write --dir ...`. Само обновление уже
выполнено; журнал можно дописать.
